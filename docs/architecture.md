# 架构说明

本文记录这套本地部署的组件划分、请求路径和几个关键设计决策。面向想改代码或排查故障的人。

## 组件拓扑

```
客户端
  │
  ├─ 7863  Go 网关 ────────────────────────┐
  │    OpenAI Chat + 账号池 + 调度器        │
  │                                        │
  └─ 8787  协议兼容层 (Python/FastAPI)     │
       只做协议转换，不碰账号               │
            │                               │
            └────── 转发到 7863 ────────────┘
                        │
                   WorkBuddy 上游
                        │
  7864  工作台 (Python) ── 通过 HTTP 调 7863 的 /_manage/*
```

### 为什么是两个进程

上游只有一种对话协议。而客户端要三种：

- OpenAI `POST /v1/chat/completions`
- OpenAI Responses `POST /v1/responses`
- Anthropic `POST /v1/messages`

Go 网关只实现了第一种。后两种由 Python 兼容层做协议转换，转成 Chat 请求后转发给 7863。这样账号池、冷却、熔断、粘性全部只有一份实现，兼容层退化成无状态转换器。

早期版本里兼容层自己管账号，结果两套系统同时刷新同一批 refresh token，互相把对方的凭据刷失效。分开之后这个故障模式消失。

### 为什么工作台是第三个进程

工作台需要读 Go 解释器不容易处理的 JSON 结构、跑 Python 辅助脚本、以及在不重新编译的情况下迭代 UI。把它做成独立 Python 进程，Go 网关就只需要暴露一组 `/_manage/*` 管理接口，前端改样式时刷新浏览器即可。

## 请求路径

一次 Chat 请求的完整链路：

1. 客户端带 `Authorization: Bearer <网关密钥>` 请求 7863
2. 网关校验密钥 → 解析 `model`，剥离 `cn:` / `global:` 前缀得到路由域
3. 选号：过滤掉冷却 / 熔断 / 暂停 / 凭据失效 / 在途已满的账号，再按四因子权重在 Top-5 短名单里加权抽签
4. 取该账号的 access token，检查剩余有效期；快过期就先刷新
5. 组装出站请求：官方客户端头族、`stream:true`、可选的提示词替换与指纹清洗
6. 上游返回 SSE；网关按 OpenAI 规范重建每一帧
7. 请求结束写一行访问日志（模型、UID、TTFB、tok/s、credit），并更新该账号的账本

非流式请求在第 6 步之后本地聚合成单个 JSON。

### 出错时的分支

| 上游信号 | 判定 | 动作 |
| --- | --- | --- |
| 429 + `soft_rate` | 软限流 | 该账号冷却 600s 起指数退避 |
| 402 / 余额耗尽 | 硬限流 | 冷却至次日 04:00 |
| 404 | 模型不可用 | 浅冷却，可换号重试 |
| 6004 | 该模型用量超限 | 只冷却这个模型，其他模型仍可用 |
| 裸 401 HTML | 凭据被上游吊销 | 硬禁用该账号（不再参与轮转） |
| 11140 | chat 通道封禁 | 重新登录才可能恢复 |
| 14018 | 积分耗尽 | 等充值或换号 |
| 11-128 | 非官方客户端 | 请求根本没进入业务层，与封禁无关 |

区分这几层很重要。把 11140 当成"token 失效"去重登，可能白费一次风险信号；把 11-128 当成封禁，会误判账号已死。

## 账号池

### 选号权重

```
权重 = 积分比例 × 10
     + 闲置补偿（每小时 +0.5，封顶 5.0）
     + 成功率 × 3
     + 快过期积分占比 × 8
```

按权重降序取 Top-5 组成短名单，再在名单内加权抽签。等权重时先随机打乱，防止每次都是同一个号（惊群）。如果所有候选都在 100ms 内被选过，退回 LRU。

"快过期积分"指的是 `pool.expiring_soon`（默认 168 小时）内会到期的积分占比 —— 那部分积分不用就浪费了，所以给高权重。

### 冷却与熔断的层级

```
账号级：冷却（时间窗） → 熔断（连续失败计数）
模型级：rate_limited_models 台账，独立 reset 时间
```

账号级冷却只影响这个账号；模型级冷却只影响这个账号的这个模型。两者叠加：一个账号可能整体健康，但某个模型在冷却中。

### 状态持久化

池状态（积分、冷却、熔断、计数、账本）原子落盘到 `data/state.json`（tmp + rename）。可选镜像到 Upstash Redis，用于多机部署。重启后从盘上恢复，不会因为重启把冷却状态清零。

## 定时任务

调度器是单进程内的循环，按北京时间找下一个触发点。

关键点：`nextWake` 只往后找时间点，所以**进程在触发时刻不在线，那一次就被静默跳过**。为此启动 45 秒后会跑一次 `RunStartupCatchup`：只对 refresh token 剩余 ≤25 天的账号逐个刷新，再补一次到期巡检。不是全池刷新 —— 刚刷过的账号零上游调用。

到期提醒有每日去重：`data/expiry-alert-day.txt` 存本地日期字符串，同一天重复巡检直接跳过。只有真的弹了通知才写标记，所以"当天无告警"不占用额度。

## 提示词与指纹

两层，可叠加：

1. `prompt.mode`
   - `passthrough`（默认）：透传客户端原始 system，只是在上游拦截时降级成中性提示词重试
   - `custom`：用 `prompt.file` 的内容替换客户端 system / developer
2. `features.sanitize_blacklist_fingerprints`：清洗出站请求体里的黑名单指纹字段

这两层都只是减少误判，不构成对上游风控的规避 —— 也不应该这么用。

## 已知边界

- **网关没有"默认模型"设置。** `resolve_model` 只剥离前缀，不提供默认值。空 `model` 会原样发给上游并返回 `11102`。所以所有客户端和文档都必须写明模型名。
- **端口是硬编码关联的。** 7863 在 `config.json`、`workbench/server.py` 的 `PORT`、`compat/server.py` 的 `uvicorn.run` 和各启动脚本里都有出现。改一处会断链。
- **重启会截断日志。** `start.ps1` 用 `Start-Process -RedirectStandardOutput`，每次启动覆盖 `server.stdout.log` / `stderr.log`。重启前的诊断信息会丢。
- **兼容层日志无界增长风险已缓解但有代价。** `compat/core/converter.py` 按 512 MB 上限轮转、保留 3 份（稳态约 2 GB）。历史上曾因为无轮转累积到 10 GB 以上。轮转只解决体积，请求体仍然是明文，所以这个文件必须按敏感数据处理。
- **保存设置会重启网关，约 4.4 秒空窗。** 落在窗口里的请求会拿到 503 / 10061。消除它需要进程内配置热加载，目前没做。
- **看门狗需要用户已登录。** 计划任务以交互令牌运行，用户没登录时不工作。这对桌面部署可以接受，但不等于服务级保障。

## 数据目录

| 路径 | 内容 | 敏感 |
| --- | --- | --- |
| `auths/` | 账号凭据（明文 JWT） | 是 |
| `data/state.json` | 池状态、冷却、账本 | 中 |
| `data/workbench-credits.json` | 余额快照 | 中 |
| `logs/server.stdout.log` | 访问日志（含 UID、模型、耗时） | 中 |
| `logs/compat.log` | **完整请求体明文** | 是 |
| `output/daily-tasks/` | 日常任务输出 | 低 |
| `runtime/` | Go 工具链、Python venv、构建缓存 | 否 |
